## 3. 性能表（可直接粘贴/替换为本机数据）

使用 [05-performance.md](05-performance.md) 的完整表。重点数字：

- AES-256-GCM 1–10 MiB：约 0.8–0.9 GiB/s。
- 100 MiB 端到端加密 1.23 s / 解密 1.16 s（本机 Edge headless）。
- PBKDF2 600k：约 178 ms；scrypt 2^17：约 637 ms、128 MiB。
- RSA-3072 签名 6.6 ms、验签 0.1 ms、keygen 470 ms。

**必须写明**：端到端基准不含 IndexedDB 写入/读取与浏览器下载落盘；实际 UI 会更慢。报告应注明硬件/浏览器/统计方法，并建议在本机重新跑。

## 5. 答辩可能追问（简答）

1. **为什么分块？** 控制内存、进度/取消、块级定位；AAD 绑定索引防重排。
2. **为什么每文件 DEK？** 文件间密钥隔离；换口令只重包 DEK；避免 GCM 密钥复用。
3. **为什么 HKDF？** 从同一 IKM 派生用途隔离的 VMK/keyringKey/KCVKey，避免跨用途复用。
4. **KCV 的作用与风险？** 精确错误提示；给离线攻击者快速校验，但 KDF 仍是主成本。
5. **证书认证做了什么？** 自签名 X.509 + SHA-256 指纹固定 + 签名者字段匹配 + 有效期覆盖 signedAt；局限是无 CA/吊销。
6. **签名覆盖什么？** 所有安全相关清单字段（算法、KDF、wrappedDEK、哈希、证书指纹等），规范化 JSON 逐字节比对。
7. **密文篡改为何不是签名先失败？** 签名覆盖清单而非密文；密文完整性由 GCM/AAD；明文哈希再与签名清单比对。
8. **改口令会重新加密文件吗？** 不会；只重包 DEK + 重签清单；导入容器跳过。
9. **备份和导出的区别？** .sfbackup 含密钥+证书+信任库用于重建；.sfkey 只含私钥+证书用于替换签名密钥。
10. **最大安全局限？** 自签名 TOFU 无法证明身份/吊销；JS 内存不可控；无抗回滚；元数据明文。
