# 06 · 安全局限

> 题目要求“至少一个安全局限说明”。以下给出 16 条，报告中可选取 6–8 条展开，建议必写：SHA-1、自签名 TOFU、JS 内存、元数据、抗回滚、安全删除。

## 1. SHA-1 弱碰撞性

- SHA-1 已被 SHAttered 实际碰撞攻破；两个不同 PDF 可以有相同 SHA-1。
- 本项目中 SHA-1 仅作为“内容哈希”演示选项；默认 SHA-256。
- RSA 签名摘要始终 SHA-256，不随内容哈希选择降级，因此即使内容用 SHA-1，签名本身仍是强哈希。
- 仍存在“内容哈希用 SHA-1 可能被碰撞替换”的风险；报告中应建议新系统禁用 SHA-1。

## 2. 自签名 X.509 + TOFU

- 没有 CA 身份背书；证书主题是用户可填写的显示名，不能证明真实身份。
- 首次信任（TOFU）可能被攻击者用自己的证书替换；只有用户线下核对完整 SHA-256 指纹才能降低风险。
- 没有 CRL/OCSP/吊销列表；移除信任是唯一“撤销”方式。
- 真实系统需要 PKI/CA、证书策略、身份核验、吊销与审计。

## 3. JS/浏览器内存不可控

- JS 字符串不可变，无法可靠擦除口令；`Uint8Array.fill(0)` 只是尽力而为。
- 解锁期间 VMK、私钥 CryptoKey、明文分块、口令输入都可能留在内存，直到 GC。
- XSS、恶意浏览器扩展、内存取证、崩溃转储可绕过。
- WebCrypto 的 CryptoKey 由浏览器管理，无法保证物理内存擦除。

## 4. 元数据未加密

- 文件名、大小、MIME、创建/签名时间、算法、KDF 参数在容器头/IDB 中明文可见。
- 攻击者可做存储/流量分析、推断文件类型与业务。
- 若需要隐藏元数据，应加密文件名/大小等字段，并设计“解锁后才能列出文件”的 UX；本项目未做。

## 5. 无抗回滚/新鲜性

- 签名只证明“这个容器由该密钥签过”，不证明“它是最新版本”。
- 攻击者可以用一个旧的合法容器替换新容器；验签仍通过。
- 需要外部版本计数器、可信日志、服务端状态或透明日志；本项目无服务端。

## 6. 安全删除不可保证

- 删除 IndexedDB 记录不等于物理擦除；浏览器缓存、SSD 磨损均衡、文件系统日志都可能残留。
- 删除密钥/文件后，攻击者仍可能从磁盘镜像恢复。
- 真实系统需要全盘加密、安全擦除/密钥销毁策略。

## 7. RSA PKCS#1 v1.5 而非 PSS

- 本项目为证书生成/验证兼容性选择 RSASSA-PKCS1-v1_5 + SHA-256。
- PKCS#1 v1.5 在正确实现下仍安全，但现代设计更推荐 RSA-PSS（或 Ed25519/ECDSA）。
- 报告应说明迁移路径：WebCrypto 支持 RSA-PSS；证书库若支持 PSS OID，可切换。

## 8. 本地时钟不可信

- 证书有效期与清单 `signedAt` 依赖本机时钟；没有可信时间戳。
- 用户可改系统时间，导致“证书在签名时有效”的判断被操纵；旧文件在新机器上可能因时钟偏差报 `E_CERT_EXPIRED`。
- 真实系统需要 TSA/可信时间或放宽有效期策略。

## 9. PBKDF2 离线猜测与 KCV oracle

- 攻击者拿到 IDB/导出文件后可离线跑 KDF 猜测口令；安全性取决于口令强度与 KDF 成本。
- KCV 让每次猜测的验证更快（HMAC 比较），但 KDF 仍是主要成本；它不存储密钥。
- 没有 HSM、速率限制、账户锁定；纯前端无法防止离线暴力。

## 10. 浏览器/OS 信任与 XSS

- 纯前端应用无法防御已失陷的 OS、键盘记录器、恶意扩展、浏览器 0-day。
- 解锁期间的 XSS 可以读取 CryptoKey/明文/口令。
- 缓解：React 默认转义、不使用 `dangerouslySetInnerHTML`、依赖最小化、建议 CSP、独立浏览器 profile；但无法根治。

## 11. 单用户、单保管库、无访问控制

- 一个浏览器 origin 一个保管库；没有多用户/角色/共享/权限。
- 没有服务端访问控制、审计服务端化、撤销、远程擦除。
- 任何能使用该浏览器 profile 的人都可以尝试解锁。

## 12. 大文件/浏览器配额限制

- 文件上限 4 GiB + chunkCount 4096；实际受 IndexedDB 配额、内存、Blob/下载策略限制。
- 解密会在内存中收集明文分块后才生成 Blob；极大文件可能 OOM。
- 当前实现不是磁盘流式解密；真实大文件系统需要分卷、流式落盘、临时加密文件。

## 13. 多标签页与自动锁定竞态

- 两个标签页同时操作同一保管库可能产生写冲突；pending 清理只处理 15 分钟前的记录以降低误删风险。
- 自动锁定不会强制取消已经在 Worker 中运行的任务；Worker 持有克隆的 CryptoKey，可能继续完成当前大文件任务。
- 没有 BroadcastChannel 锁定同步/互斥锁。

## 14. 审计日志不抗篡改

- 审计日志存在本机 IndexedDB，仅记录元数据；本机攻击者可删除/改写。
- 没有哈希链、签名链、远程不可篡改存储；不能作为强法律证据。
- UI 已明确说明该局限。

## 15. 导入容器的口令与重包边界

- 导入的 `.sfv` 保留原 KDF/KCV/签名；修改本机主口令**不会**重包它。
- 解密导入容器需要使用容器创建时的原口令；用户可能误以为“当前保管库口令”可用。
- 若需要统一口令，应解密后重新加密/重新签名，或设计容器迁移流程。

## 16. 其他

- `fileId`/文件名/MIME 未作为安全边界；MIME 仅展示，不执行。
- 没有防病毒/内容扫描；下载文件可能包含恶意内容。
- 没有服务端速率限制/账户锁定；离线攻击不可控。
- 没有密钥轮换的一键 UI；通过导入/恢复另一把 `.sfkey`/`.sfbackup` 实现，旧证书保留信任。
- 依赖 npm 供应链；未做 SBOM/签名验证/依赖审计（建议 `npm audit`、锁文件、最小依赖）。
- 路径含中文/空格在个别 Node 工具上可能异常；本项目已验证本机可构建/测试。

## 报告中如何写

建议结构：

1. 威胁模型（资产/攻击者/信任边界）。
2. 每条局限：**描述 → 影响 → 本项目为何接受/如何缓解 → 真实系统应如何做**。
3. 至少给出一个可现场演示的局限（SHA-1 碰撞 PDF 或 TOFU 证书替换）。
4. 不要把“纯前端”“没有服务端”写成实现缺陷；应作为设计边界说明。
